# Design critique: accepted findings (judge-ranked)

## A01 [critical] (security-safety, git-merge)

Where: docs/ARCHITECTURE.md section 6 (request guards, every /api route), section 2 principle 4, section 7 (@human posts); server/http.js guard(); ui/lib/api.js

Problem: Merges findings 14 and 25. The owner API has no secret. The Host check, the Origin check and the fixed header X-WorkShop: 1 stop browsers only (confirmed in http.js). Every agent knows the port from its MCP URL and has a shell, and the sandbox note in providers/claude.js says localhost stays reachable. One curl can ship the truck, post PASS as @human, approve the plan, set safety:'trusting' or replace a key. A prompt injection from a web page in a research task is enough. The three gates of principle 4 are then advice, not gates.

Fix: Add to section 6: 'Owner key. At boot the hub makes a random 256-bit ownerKey. It lives in memory only: never in data/, logs, state, events, prompts or a child environment. index.js prints WORKSHOP_READY <url>#k=<ownerKey> and the launcher loads that URL. The UI posts the key once to POST /api/session { k }, gets a cookie (HttpOnly; SameSite=Strict; Path=/) and removes the fragment. Every /api/* route, GET and SSE included, answers 401 without the cookie (constant-time compare). /mcp/:token is the only route that takes an agent token, and an agent token opens nothing under /api. Posts as @human and all owner actions exist only behind the cookie.' Keep the Host and Origin checks.

## A02 [critical] (state-machine, git-merge, cost-comms, owner-fit)

Where: ARCHITECTURE.md section 4 (Agent.taskId, Agent.sessionId), section 7 (board.view cursor, turn gate), section 10 Runner ('update agent.sessionId'), section 12 Crew ('Reuse an idle maker persona', 'retired') and Turns ('fresh sessions')

Problem: Merges 1, 22a, 43, 60b. There is one agent.sessionId and one board cursor per persona, but a persona runs several sessions. (a) Default crew, one boss: it plans in session S1, then reviews T1 in a fresh session S2, and the runner stores S2. The next owner change resumes S2: a review of one task with no memory of the plan. (b) Maker @m3 posts DONE T12 and is idle. The crew rule reuses it for T15 with a new session. Then FIX for T12 arrives: the hub resumes the T15 session in the T15 bench, or wakes nobody, and T12 stays in rework. (c) A review prompt shows the boss its board delta and moves the cursor, so the long session never sees those posts. The turn gate then makes a review session answer a planning question. (d) An idle persona of another model is retired and never hired again, so a long job shows a stream of new names, not a crew.

Fix: Section 4: add Task.sessionId (the maker work session; its cwd is always benchDir), Task.reviewSessionId, Job.qa { round, sha, sessionId } and Agent.boardCursor. Agent.sessionId is the main session of a boss or manager only. Section 10: runner.run(agentId, { sessionId, resume, ... }) returns sessionId; the runner never writes agent.sessionId; the orchestrator stores the id on the work item. Section 12, three turn classes: main (plan, plan merge, owner change, report, manager digest, answers) uses agent.sessionId; work (maker task turns) uses task.sessionId; aux (buddy, review, QA, audit, consult) uses a session kept on the task or job. An aux turn gets a board view scoped to its task that does not move agent.boardCursor. The turn gate and board.openFor apply to main and work turns only. Mail that arrives during an aux turn waits, and the hub runs a main turn for it before it gives that agent another aux turn. Crew: 'A maker persona is bound to one task from hire until that task is merged or cancelled, or gets another assignee. It never gets a second task and is never set off while bound. crew.makers caps tasks in working or rework; the 8 bench spots cap open benches. Hire order: a free persona with the wanted model, then an off persona with that model (same name and seed), then a new persona. FIX, ANS and hub EVT for task T resume task.sessionId in task.benchDir as task.assigneeId. A buddy is a maker of the other lab whose own task is not in working or rework, else a new hire.'

## A03 [critical] (git-merge, security-safety, state-machine, cost-comms)

Where: ARCHITECTURE.md section 4 (Delivery has no head sha), section 7 wake rule, section 9 steps 4-5, section 12 Hand-in, Review, Integrate; server/prompts.js reviewPrompt ('Run the check when it helps')

Problem: Merges 17, 30 (part A), 12, 48.3, 29.1. A verdict names a message id, not a commit, and the bench stays writable after DONE. Normal paths break this: an ASK from a peer wakes the maker with write access while T12 is in review; a reviewer with a shell runs a formatter; the check rewrites a tracked file (lockfile, snapshot). Results: the reviewer passes a diff that is not what merges; an uncommitted change is silently left out, so the check ran on another tree; a dirty tree makes syncBench throw and passed work sticks in integrating. PASS also takes effect at the post, so the hub can start sync and check in the bench while the reviewer still works there. A maker can post DONE and then BLOCK in one turn: two states at once. In a shared bench a maker can also leave files that set the cross-lab reviewer's rules.

Fix: Section 4 Delivery: add baseSha and headSha (the bench head after sync and a green check; the hub sets it at the end of the pipeline). Section 9 and 12 rules: (1) After runCheck the hub runs git reset --hard <headSha> and git clean -fd (ignored files stay). (2) Buddy checks and reviews run in a hub-made clone at headSha (data/work/<job>/<task>.rev, removed when the task is merged), never in the bench. The hub first removes agent-config files from that working tree (.agents/, GEMINI.md, AGENTS.md, .claude/, CLAUDE.md, .mcp.json), then writes its own adapter files, .shop/TASK.md and .shop/CHECK.log. The prompt gives git diff <baseSha> <headSha> and the hub's check result; the line 'Run the check when it helps' goes. (3) A verdict is stored with headSha and takes effect when the reviewer's turn ends; the hub may stop that turn with SIGINT after a valid verdict. (4) Freeze: from an accepted DONE until the hub sets rework, the maker's own open ASK and BLOCK items for the task close as cancelled, the post tool refuses DONE, BLOCK and ASK from it for that task (E_CLOSED), and any wake of it runs with access read and the first line 'Your work is in review. Answer only.' (5) Section 9 signature: git.integrate(..., { expectHead }) (gitops.js has it). expectHead is headSha, or the hub's own sync merge whose parents are exactly headSha and the integration head; the check runs again on that merge, then rule 1 again. Before integrate and before a rework wake the bench must be clean at the expected head; if it is not, the hub resets it to headSha and posts EVT #ops. commitAll runs only at hand-in.

## A04 [critical] (state-machine, git-merge, security-safety, owner-fit)

Where: ARCHITECTURE.md section 6 (POST /ship { upTo? }, GET /truck, POST /api/reveal), section 9 step 6, section 12 Delivering and Owner actions, section 13 truck states; server/gitops.js ship(), truck()

Problem: Merges 2, 13, 20, 30 (part B), 53, 9 (run A). (a) Ship without upTo moves the target to the integration head at click time. A crate that merged two seconds before the click ships although the owner never saw it. Gate 3 breaks with no bug and no bad actor. (b) Ship is fast-forward only. On a job that runs two days on a live repo the owner commits once to main, and ship answers 'moved ... Nothing was changed' (confirmed in gitops.js). The contract has no next step: the reviewed work sits on the truck until the owner merges by hand in a terminal. (c) The contract does not say when ship is allowed. The rule 'a ship that leaves the truck empty -> report, done' can close a job that still has open tasks after a partial ship. (d) The report ('how to run it, what is not done') is written after the owner approved, and reveal opens a folder that does not hold the cargo yet.

Fix: Section 6: GET /truck -> { headSha, behind, deliveries, stat, files, reqs:{open,failed,verified,waived}, report }. POST /ship { sha } (required): sha is the headSha the panel showed, or the mergeSha of a loaded delivery. The hub ships exactly that commit, never 'head now'. It accepts only a commit on the first-parent chain of job.intSha (a delivery merge or a refresh merge). Crates merged after sha stay loaded and the answer says how many. Section 9: git.truck returns behind and headSha. Section 12: 'Ship is allowed in running, qa, delivering and paused when a delivery is loaded. done needs all of: status delivering, truck empty, no open task, every requirement verified or waived. Refresh truck: when git.truck().behind > 0 at entry to qa or at a ship request, the hub merges the target branch into a scratch clone of the integration head and runs the head check there (A22). Clean and green: _int fast-forwards to that merge, the truck stays loaded, and the owner gets a notice that lists the new commits (Your branch moved. Look again, then ship.). Conflict or red check: _int does not change. With no open task (job in qa or delivering) the hub adds a catch-up task (domain fix, zones **, its bench starts with that merge in place) and the job returns to running. With open tasks the ship answer names the files and the refresh runs again at entry to qa. The lead writes job_report on entry to delivering. The Truck panel shows the report and, before that, n requirements not verified beside Ship.' Section 13: truck docked (no cargo), loading (cargo, job not in delivering), ready (job in delivering). Section 13b: POST /api/reveal { jobId, what:'truck' } makes a clone of the truck head at data/work/<job>/_preview and shows it in Finder, so the owner can run the cargo before approval.

## A05 [critical] (state-machine, cost-comms, owner-fit)

Where: ARCHITECTURE.md section 2 principle 5, section 4 Req, section 6 (no requirement routes), section 8 and 12 (task_add, task_cancel, req_verify), section 12 QA and requestChanges; server/prompts.js ownerChangePrompt, qaPrompt

Problem: Merges 3, 37, 52, 39. The ledger is frozen after planning, in both directions. (a) The owner clicks Request changes: 'also add CSV export'. No tool or route creates a requirement, so the new task has reqs []. It can fail and be cancelled, because the cancel rule only guards tasks that serve a requirement. QA checks the old list again, all pass, confetti. The wish is dropped silently: the owner's named pain. (b) waived is a status, but nothing can set it. A requirement that cannot be met loops QA -> task_add -> QA with no cap. (c) req_verify with 11 of 12 results, or a failed result without task_add, leaves the job in qa with no exit. (d) A stale QA turn can call req_verify after an owner change moved the job back to running, and jump it to delivering with a task open. (e) With one boss, the planner verifies its own plan.

Fix: Section 4: Req { id, text, source:'plan'|'owner'|'boss', status, evidence, waivedReason }. Section 6: POST /api/jobs/:id/reqs { text } and POST /api/jobs/:id/reqs/:rid/waive { reason }, valid from plan_review on (Blueprint panel: Add requirement, Waive). Section 12: 'requestChanges and the add route first create a Req (source owner, the owner's words) and then wake the lead boss. task_add in that turn must cite the new id. A Req with no open or merged task at turn end: one nudge, then an owner notice. Tool req_add { text, why } (boss, and the agent assigned to an audit or QA turn): source boss, non-blocking owner notice. task_cancel and a task_update of reqs are refused when they leave a requirement that is not waived without an open or merged task. Every entry to qa sets job.qa = { round+1, sha: integration head } and every requirement that is not waived to open. req_verify is accepted only from the agent assigned to the QA turn, only while status is qa and the integration head equals job.qa.sha, and only with a result for every open requirement (the error lists the missing ids). Each evidence needs a pointer to a path that exists at that sha. A failed requirement with no serving task when the QA turn ends: one nudge, then the lead boss is woken once, then an owner notice with Waive, Add task, Stop job. limits.maxQaRounds (3): after it the job is paused (pauseReason qa) with the failed requirements listed. QA goes to a boss of another lab than the lead, else a manager of another lab, else the lead in a fresh session.'

## A06 [critical] (state-machine, git-merge, security-safety, owner-fit, cost-comms)

Where: ARCHITECTURE.md section 12 Task flow (attempts, task_retry, 'another reviewer'), QA, Budget, pauseJob; section 14b DEFAULT_SETTINGS (budgetUsd: null); section 8 task_add, task_retry; section 13b job chip ($cost)

Problem: Merges 4, 19 (baseline), 31, 50, 51 (cost label). No loop has a cap and money has no default cap. (a) Existing repo: the boss sets check_cmd 'npm test'. It is already red there, or needs network. Every hand-in fails, every task burns 3 reworks, every manager calls task_retry. The text does not say if a retry resets attempts: the task fails at once, or the cycle never ends. budgetUsd is null, so the crew burns API money or a subscription window all night and merges nothing. (b) A review FIX and an integrate send-back do not raise attempts, so reviewer and maker can ping-pong without limit. (c) 'No verdict after a nudge: another reviewer' has no answer in a solo crew. (d) The budget is checked between turns and pause lets running turns finish: six 45-minute top-tier turns overshoot it. (e) In subscription mode the chip shows a list-price estimate as $cost (the CLI's number is a client-side estimate, not a bill), so a budget would pause a job that cost nothing.

Fix: Section 12 Baseline gate: 'Existing project: after plan_submit validates and before the plan is applied, the hub runs the head check (A22) twice; the job stays in planning. It stores project.baseline { sha, ok, flaky, ms, tail }. Red, flaky, or slower than half of checkTimeoutMin: the lead boss is resumed once with the tail to submit again. A second failure pauses the job (pauseReason baseline) with the tail for the owner. New project: the same run after T1 merges; red: the lead is woken to add a fix task.' Counters: 'task.attempts rises on every return to rework (pipeline refusal, review FIX, failed check at integrate), not on a merge conflict found by the hub. task_retry resets attempts and raises task.retries; limits.maxRetries 2. limits.maxTasksTotal (60) counts plan tasks plus task_add. At a limit the tool returns an error. Reviewer no-show: at most 2 reviewers per delivery, then it waits for PASS or FIX from @human (owner notice). Circuit breaker: a limit reached, or 3 hand-ins in a row from different tasks refused for the same cause (check, zone, guard, setup), pauses the job (pauseReason caps) with an owner notice.' Budget: 'job.cost = { billedUsd, estUsd, inTok, outTok }. billedUsd counts turns of labs in apikey mode. estUsd counts subscription turns and the UI labels it est. at API prices. budgetUsd applies to billedUsd. POST /api/jobs refuses a job without budgetUsd when a usable lab is in apikey mode (the Work Order panel pre-fills a default). In apikey mode the Claude adapter passes --max-budget-usd min(limits.turnUsd, remaining). At the budget the runner stops the running turns of apikey labs with SIGINT (sessions resume later) and the job pauses (pauseReason budget). A turn with usd null is priced from tokens and registry prices, for every lab. The agy settings pin useG1Credits:false.'
